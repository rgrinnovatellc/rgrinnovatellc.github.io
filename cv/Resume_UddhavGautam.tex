\thread{Research Highlights}

\project{ZeroDown}{: on-the-fly eBPF security-policy updates for microcontrollers}{In preparation, IEEE IoT-J}
\begin{itemize}[leftmargin=3em]
 \item Idea: the device's owner writes its security policy as one versioned YAML file --- the rules, exceptions for particular peers, and the name of the eBPF program that decides each event --- so a change means editing the file, not the firmware
 \item Built the system that installs a new policy file on a Bluetooth Low Energy (BLE) device and activates it without a reboot, instead of waiting months for a firmware update and a restart
 \item In hardware tests, all 72 updates applied without a reset, taking a median 2.8\,s; in a separate 60-update test with a peer connected, the connection never dropped and the device's notifications to the peer paused for a median 2.5\,s
 \item Designed the update process: authenticated delivery, crash-consistent storage in two flash slots, and a confirmation step --- the device keeps a new policy only if the owner reconnects and confirms it, and reverts it otherwise
 \item Protected against bad updates: in all 7 tests with a corrupted or interrupted update, the existing policy stayed in place; and when a new policy locked the owner out, resetting the device restored the previous one in all 120 trials
 \item Hardened the eBPF interpreter that runs the rules (step limit, memory checks, divide-by-zero fix): no crash in 146.9M host-side fuzzing executions; deciding one event takes about 0.3\,ms
\end{itemize}

\project{Android 17 JobScheduler}{: its reports of why jobs wait can be wrong while its scheduling is right}{}
\subitemnote{Lost Boundaries (in preparation, IEEE TMC); Correct Decisions (under review, ACM HotMobile '27)}
\begin{itemize}[leftmargin=3em]
 \item Found that Android 17's report can show a job waiting longer than it has existed, and show a system policy (App Standby) holding the job longer than the app's own requested delay --- pointing a developer at the wrong cause (30 of 30 qualifying emulator attempts)
 \item Showed the reported wait shrinking by over 8\,s while the job kept waiting --- a decrease no correct count can produce (2 of 2 emulator boots)
 \item Traced the cause: two wait conditions reported under one reason share one start time; the second to start waiting overwrites it, and the first to finish deletes it --- so later waits are measured from the wrong moment, even from the job's creation
 \item Proved that two different wait histories can leave identical stored data, so no change to the calculation alone can report both correctly
 \item Explained why the error goes unnoticed: scheduling never reads the reported durations, so it stays correct, and none of the 7 upstream tests for this report checks the duration of a shared reason
 \item Proposed a 4-part test format (property, history, observations, assertion) to catch such errors
 \item Built a one-commit fix: on both repaired emulator images, neither the ranking reversal nor the reported~decrease~reappeared
\end{itemize}

\project{AIE Verification}{: approving AI-written code and software releases}{In preparation, ACM TOSEM}
\begin{itemize}[leftmargin=3em]
 \item Showed that AI-written tests can pass wrong code: in 25 constructed LLM coding tasks (Codex CLI), all passed their own tests, including 12 labeled flawed for following a prompt's wrong assumption
 \item Wrote checks from the real requirement: they rejected all 12 flawed results and accepted the other 13
 \item Defined 3 conditions for trusting an approval: it checks the real requirement, its inputs are controlled outside the build pipeline, and it applies to the exact file delivered
 \item Built a release check in an Android app's release CI/CD pipeline: it rejected all 9 bad test inputs and accepted all 4 good ones
\end{itemize}
